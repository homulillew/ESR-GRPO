# ESR-GRPO 实验执行手册

本文档把 ESR-GRPO 方案中的三个实验拆成可以逐项执行、检查和复现的任务。运行环境为 Linux。文档中的路径均通过环境变量指定，上传到服务器后只需要修改开头的根目录。

本文档同时区分三种实现状态：

- **可直接运行**：仓库已有脚本，依赖服务就绪后可以执行。
- **需要外部服务**：实验脚本已完成，但策略模型、验证器、Judge 或检索服务需要单独启动。
- **尚缺运行器**：目前只有实验配置或分析代码，不能把配置文件直接当作可执行脚本。

## 1. 实验总览

| 实验 | 任务 | 主要模型 | 当前入口 | 状态 |
|---|---|---|---|---|
| 实验一 A | CPU 单元测试和离线 episode | 模拟策略 | `scripts/common/run_all_cpu_checks.sh` | 可直接运行 |
| 实验一 B | BrowseComp-Plus Benchmark 验证 | AREX-Turbo + Qwen3-32B | `exper/arex_bcplus_native/run_experiment.sh` | 需要外部服务 |
| 实验一 C | 4B ESR-GRPO 训练链路验证 | Qwen3.5-4B | `run_esr_4gpu.sh` | 需要外部服务 |
| 实验二 A | Evidence 使用情况分析 | 实验一轨迹 | `analyze_experiments.py` | 可分析已有轨迹 |
| 实验二 B | TaskState 和状态协议检查 | 实验一轨迹 | `audit_state_protocol.py` | 可直接运行 |
| 实验二 C | 动作信用准确性检查 | 轨迹 + 人工标签 | `inspect_credit_trace.py`、`validate_credit_labels.py` | 可直接运行 |
| 实验二 D | `full_evidence` 与 `summary_only` 消融 | 4B 策略模型 | 只有 `evidence_ablation.yaml` | 尚缺运行器 |
| 实验三 A | AREX-Turbo 推理基线 | AREX-Turbo | 复用 `run_benchmark.py` | 需要外部服务 |
| 实验三 B | 全轨迹 GRPO | Qwen3-30B-A3B | `run_baseline_4node.sh grpo` | 依赖 ECHO 多节点环境 |
| 实验三 C | ECHO | Qwen3-30B-A3B | `run_baseline_4node.sh echo` | 依赖 ECHO 多节点环境 |
| 实验三 D | ESR-GRPO 正式训练 | Qwen3-30B-A3B | 当前只有 4 GPU 验证入口 | 尚缺正式多节点运行器 |

建议严格按照以下顺序执行：

```text
数据和环境检查
→ 实验一 A：CPU 自检
→ 实验一 B：AREX-Turbo Benchmark 验证
→ 实验一 C：4B ESR-GRPO 训练链路验证
→ 实验二：状态、Evidence 和动作信用分析
→ 根据实验二结果冻结方案
→ 实验三：四条方法使用相同设置训练和评测
```

## 4. 公共服务

实验一的真实推理需要检索、策略、验证器和 Judge。实验一 C 与实验三训练由 ECHO 内部启动策略 rollout，但仍需要检索、验证器和 Judge。

### 4.1 端口约定

| 服务 | 示例地址 | 作用 |
|---|---|---|
| Retrieval | `http://127.0.0.1:8000` | `search` 和 `open_page` |
| Verifier | `http://127.0.0.1:8001/v1` | `verify_answer` 在线验证 |
| Policy | `http://127.0.0.1:8002/v1` | 实验一和 AREX-Turbo 推理 |
| Judge | `http://127.0.0.1:8003/v1` | 计算最终奖励和最终评测 |

端口只用于示例。服务在其他机器上时，应使用实际 IP 或域名。

### 4.2 启动 BM25 检索服务

4 GPU 训练会占用本机全部训练卡。Pipeline 验证优先使用 CPU BM25，避免密集检索模型与训练进程争抢显存。

```bash
source "$ESR_ROOT/.venv/bin/activate"

python "$ECHO_ROOT/examples/sglang_multiturn/browsecomp_retrieval_server.py" \
  --mode bm25 \
  --corpus_file "$CORPUS_FILE" \
  --bm25_cache "$CACHE_ROOT/browsecomp_bm25_cache.pkl" \
  --pool_workers 8 \
  --host 0.0.0.0 \
  --port 8000
```

第一次启动会根据 `corpus.parquet` 构建 ECHO 自己的 BM25 缓存。后续启动会直接读取缓存。

服务检查：

```bash
curl -fsS http://127.0.0.1:8000/health

python -P scripts/experiment1_pipeline/check_retrieval_roundtrip.py \
  --retrieval-url http://127.0.0.1:8000 \
  --query "example entity and event" \
  --top-k 5 \
  --open-count 3
```

### 4.3 密集检索注意事项

ECHO 的密集检索服务缓存应包含 `docids`、`contents` 和 `embeddings`。本地下载的 `Tevatron/browsecomp-plus-indexes` 是 Tevatron 发布的索引，不能在未检查格式的情况下直接填入 ECHO 的 `--dense_cache`。

需要使用 ECHO 密集检索时，可以让服务根据语料重新构建缓存：

```bash
CUDA_VISIBLE_DEVICES=0 \
python "$ECHO_ROOT/examples/sglang_multiturn/browsecomp_retrieval_server.py" \
  --mode dense \
  --corpus_file "$CORPUS_FILE" \
  --model "$MODEL_ROOT/Qwen--Qwen3-Embedding-0.6B" \
  --device cuda:0 \
  --batch_size 64 \
  --dense_cache "$CACHE_ROOT/browsecomp_echo_dense_0.6b.pkl" \
  --host 0.0.0.0 \
  --port 8000
```

正式对比实验必须为所有方法固定同一个检索器、检索缓存、top-k 和语料版本。密集检索服务最好运行在独立 GPU 或独立机器上。

### 4.4 启动 OpenAI 兼容模型服务

以下是 vLLM 命令模板。GPU 编号、tensor parallel 数量和显存比例必须根据服务器资源调整。

AREX-Turbo 策略服务：

```bash
CUDA_VISIBLE_DEVICES=0 \
vllm serve "$MODEL_ROOT/BAAI--AREX-Turbo" \
  --served-model-name BAAI/AREX-Turbo \
  --host 0.0.0.0 \
  --port 8002 \
  --tensor-parallel-size 1
```

Qwen3-32B 验证器：

```bash
CUDA_VISIBLE_DEVICES=1,2 \
vllm serve "$MODEL_ROOT/Qwen--Qwen3-32B" \
  --served-model-name Qwen3-32B \
  --host 0.0.0.0 \
  --port 8001 \
  --tensor-parallel-size 2
```

Judge 可以使用另一个 Qwen3-32B 服务：

```bash
CUDA_VISIBLE_DEVICES=3,4 \
vllm serve "$MODEL_ROOT/Qwen--Qwen3-32B" \
  --served-model-name Qwen3-32B \
  --host 0.0.0.0 \
  --port 8003 \
  --tensor-parallel-size 2
```

如果资源不足，Verifier 和 Judge 可以指向同一个 OpenAI 兼容服务，但必须分别记录二者的提示、采样参数和用途。4 GPU 训练节点通常无法同时承载训练、32B Verifier 和 32B Judge，应将外部服务部署到其他 GPU 节点。

检查模型服务：

```bash
curl -fsS http://127.0.0.1:8001/v1/models
curl -fsS http://127.0.0.1:8002/v1/models
curl -fsS http://127.0.0.1:8003/v1/models
```

## 5. 实验一：验证 Benchmark 和 ESR-GRPO 完整链路

### 5.1 实验目的

实验一回答两个问题：

1. BrowseComp-Plus 的数据、固定语料检索、策略推理和最终评测是否正常。
2. ESR-GRPO 是否能完成 `rollout → 最终奖励 → 动作信用掩码 → GRPO 更新`。

实验一只用于判断流程是否正确，不用于给出最终方法结论。

### 5.2 实验一 A：CPU 自检和离线 episode

配置：`configs/experiment1/pipeline.yaml`

脚本：

- `scripts/common/run_all_cpu_checks.sh`
- `scripts/experiment1_pipeline/run_smoke_episode.py`

一键执行：

```bash
cd "$ESR_ROOT"
source .venv/bin/activate
bash scripts/common/run_all_cpu_checks.sh
```

该脚本依次运行 Python 编译检查、单元测试和一条确定性 episode。

预期输出：

```text
outputs/smoke/
├── episode.sqlite
├── episode.json
└── credit.json
```

验收标准：

- 所有单元测试通过。
- Evidence 保存后不再被修改。
- TaskState 版本只追加，不覆盖旧版本。
- 未覆盖 Evidence、未验证或仍有 gaps 时不能提交。
- 信用掩码只覆盖被选中完整动作的策略 token。

### 5.3 实验一 B：AREX-Turbo Benchmark 验证

配置：`configs/experiment1/benchmark.yaml`

AREX-Turbo 原生基线已经独立实现于 `exper/arex_bcplus_native/`。该入口使用 AREX 的 `search / visit / update_context / finish` XML 协议，保存完整原始响应、逐轮推理和工具结果，并使用 BC-Plus 官方风格 Judge 提示评测。运行命令以 `exper/arex_bcplus_native/README.md` 为准。

本节后续的 `scripts/experiment1_pipeline/run_benchmark.py` 使用 ESR-GRPO 六工具协议，适合统一工具协议对照，不代表 AREX 原生基线。

实验设置：

| 项目 | 设置 |
|---|---|
| 数据划分 | `validation` |
| 样本数 | 先 10 题，再 100 题 |
| 策略模型 | `BAAI/AREX-Turbo` |
| 检索 top-k | 5 |
| 最终 Judge | Qwen3-32B |

#### 第一步：完整预检

```bash
python -P scripts/experiment1_pipeline/preflight.py \
  --dataset "$DATASET_FILE" \
  --split-manifest "$SPLIT_FILE" \
  --qrels "$QRELS_FILE" \
  --retrieval-health-url http://127.0.0.1:8000/health \
  --policy-models-url http://127.0.0.1:8002/v1/models \
  --verifier-models-url http://127.0.0.1:8001/v1/models \
  --judge-models-url http://127.0.0.1:8003/v1/models \
  --output outputs/exp1/benchmark/preflight.json \
  --strict
```

说明：当前 `preflight.py` 的语料本地检查参数名是 `--corpus-jsonl`，而现有语料为 parquet，因此这里通过检索服务 roundtrip 检查固定语料，不传该参数。

#### 第二步：10 题最小真实实验

```bash
python -P scripts/experiment1_pipeline/run_benchmark.py \
  --dataset "$DATASET_FILE" \
  --split-manifest "$SPLIT_FILE" \
  --split validation \
  --limit 10 \
  --retrieval-url http://127.0.0.1:8000 \
  --model-base-url http://127.0.0.1:8002/v1 \
  --model BAAI/AREX-Turbo \
  --verifier-base-url http://127.0.0.1:8001/v1 \
  --verifier-model Qwen3-32B \
  --output-dir outputs/exp1/benchmark_10
```

#### 第三步：检查单条轨迹

```bash
python -P scripts/experiment1_pipeline/inspect_episode.py \
  outputs/exp1/benchmark_10/stores/<query_id>.sqlite \
  --show-evidence-content \
  --output outputs/exp1/benchmark_10/inspection_<query_id>.json
```

至少检查三条轨迹：一条正确、一条错误、一条工具调用较多。

#### 第四步：扩展到 100 题

```bash
python -P scripts/experiment1_pipeline/run_benchmark.py \
  --dataset "$DATASET_FILE" \
  --split-manifest "$SPLIT_FILE" \
  --split validation \
  --limit 100 \
  --retrieval-url http://127.0.0.1:8000 \
  --model-base-url http://127.0.0.1:8002/v1 \
  --model BAAI/AREX-Turbo \
  --verifier-base-url http://127.0.0.1:8001/v1 \
  --verifier-model Qwen3-32B \
  --output-dir outputs/exp1/benchmark_100
```

已有 SQLite 文件会被跳过，因此中断后可以使用同一条命令继续。

#### 第五步：最终评测

```bash
python -P scripts/experiment1_pipeline/evaluate_runs.py \
  --dataset "$DATASET_FILE" \
  --qrels "$QRELS_FILE" \
  --runs outputs/exp1/benchmark_100/runs \
  --judge-base-url http://127.0.0.1:8003/v1 \
  --judge-model Qwen3-32B \
  --output outputs/exp1/benchmark_100/evaluation.json
```

主要输出：

```text
outputs/exp1/benchmark_100/
├── stores/<query_id>.sqlite
├── trajectory_<query_id>.json
├── runs/<query_id>.json
└── evaluation.json
```

验收标准：

- 所有题目能找到标准答案。
- 所有检索 docid 都来自固定语料。
- `search → open_page` 能按 docid 读取完整正文。
- Judge 解析错误率不超过 1%。
- 输出中没有大规模空答案、服务错误或非法工具调用。
- 记录 Accuracy、Evidence Recall、Calibration Error 和平均工具调用数。

### 5.4 实验一 C：4B ESR-GRPO 训练链路验证

配置：`configs/experiment1/pipeline.yaml`

脚本：`scripts/experiment3_training/run_esr_4gpu.sh`

#### 第一步：安装 ECHO 钩子

`run_esr_4gpu.sh` 当前不会检查 Judge 地址。若这些变量没有设置，ECHO 奖励函数可能访问错误的默认端口。

#### 第四步：运行 50 步训练

```bash
export ESR_STORE_DIR="$ESR_ROOT/outputs/exp1/esr_4b/stores"
export CHECKPOINT_DIR="$ESR_ROOT/outputs/exp1/esr_4b/checkpoints"
export EXPERIMENT_NAME=qwen4b-bcp-esr-pipeline

export TOTAL_TRAINING_STEPS=50
export TRAIN_BATCH_SIZE=8
```

显存不足时，优先依次降低：

4. `N_RESP`。
5. `ROLLOUT_GPU_MEMORY_UTILIZATION`。

```bash
python scripts/experiment3_training/inspect_training_log.py \
  outputs/exp1/esr_4b/train.log \

python scripts/experiment2_analysis/audit_state_protocol.py \
  --stores outputs/exp1/esr_4b/stores \
  --recursive \

python scripts/experiment2_analysis/analyze_experiments.py \
  --stores outputs/exp1/esr_4b/stores \
  --output outputs/exp1/esr_4b/trajectory_summary.json

python scripts/experiment3_training/debug_advantage.py
```

如果 ECHO 导出了逐段 rollout metadata，再执行：

```bash
python scripts/experiment3_training/inspect_rollout_metadata.py \
  <rollout_segments.jsonl> \
  --output outputs/exp1/esr_4b/rollout_metadata_audit.json \
  --strict
```

验收标准：

- Evidence、TaskState 和动作账本能够完整保存。
- 六种动作能够按协议执行。
- 合法提交才获得最终奖励。
- 最终奖励只写入最后一个 rollout 分段。
- 只有成功、合法提交且组内优势为正的轨迹获得 ESR 动作信用。
- 被选动作的全部策略 token 进入掩码，其他动作不进入。
- loss、KL、clip fraction、梯度范数中没有 NaN 或 Inf。
- 记录组内所有最终奖励相同、因而 GRPO 优势为零的 batch 比例。

实验一通过条件：Benchmark 真实推理正常，4B 训练完成 50 至 100 步，状态协议审计通过，动作掩码没有明显过稀或过密。

## 6. 实验二：验证 Evidence、TaskState 和动作信用规则

### 6.1 实验目的

实验二使用实验一的真实轨迹检查三个假设：

1. 保存原始 Evidence 能提高事实准确性，或减少重新搜索成本。
2. TaskState 字段能表达主要证据关系，协议约束没有被绕过。
3. 系统选择的正信用动作与人工判断的关键动作具有较高一致性。

实验二不能接触最终测试划分。bad case 分析和方案修改只能使用训练或验证划分。

统一设置：


#### `full_evidence` 与 `summary_only` 消融

| 变体 | 保存原文 | 允许 `read_evidence` |


预期命令接口：


以上两条命令是待实现接口，不是当前可执行命令。

### 6.4 实验二 C：动作信用准确性

配置：`configs/experiment2/credit_audit.yaml`

样本计划：

| 轨迹类型 | 数量 |
|---|---:|
| 成功轨迹 | 50 |
| 失败轨迹 | 50 |

先查看系统选择的动作：

```bash
python -P scripts/experiment2_analysis/inspect_credit_trace.py \
  "$EXP1_STORES/<query_id>.sqlite" \
  --selected-only \
  --output "outputs/exp2/<query_id>.credit.json"
```

人工标签使用动作 ID，不使用 turn ID。JSONL 格式：

```json
{"episode_id":"query-id","selected_action_ids":["a3","a7"],"annotator":"name","notes":""}
```

假设标签保存在 `data/annotations/credit_labels.jsonl`，执行：

```bash
python -P scripts/experiment2_analysis/validate_credit_labels.py \
  --stores "$EXP1_STORES" \
  --labels data/annotations/credit_labels.jsonl \
  --output outputs/exp2/credit_label_audit.json \
  --strict
```

也可以在总体分析中加载标签：

```bash
python -P scripts/experiment2_analysis/analyze_experiments.py \
  --stores "$EXP1_STORES" \
  --labels data/annotations/credit_labels.jsonl \
  --output outputs/exp2/analysis_with_labels.json
```

主要指标：

- Precision：系统选择的动作中，人工认为有贡献的比例。
- Recall：人工认为有贡献的动作中，被系统选中的比例。
- F1。
- Mask density：被选策略 token 占全部策略 token 的比例。
- 误报和漏报的动作类型分布。

最低验收目标为 Recall 不低于 0.8。所有误报都应人工复核。证据关系回溯是关系归因，报告中不要把这些指标称为因果准确率。

### 6.5 实验二 D：bad case 迭代

每轮修改按以下顺序进行：


## 7. 实验三：完整训练和 Benchmark 对比

### 7.1 实验目的

实验三使用实验二冻结的方案，在相同数据、初始模型、检索器、工具预算、rollout 数量和 Judge 下比较四种方法。

| 方法 | 状态管理 | 信用范围 |
|---|---|---|
| AREX-Turbo | AREX 原生协议或统一工具协议 | 不训练，只做推理基线 |
| 全轨迹 GRPO | 不使用 ESR 状态 | 全部策略 token |
| ECHO | ECHO action/finding 摘要 | ECHO 选择的分段或 token |
| ESR-GRPO | Evidence + TaskState | 回溯后选中的完整动作 |

正式比较前必须冻结：

- `v1.json` split manifest 和文件哈希。
- 固定语料、索引、检索模型和检索缓存。
- top-k、snippet 长度、`open_page` 长度和总工具预算。
- 初始 checkpoint。
- 训练 batch、每题 rollout 数量、采样温度和最大响应长度。
- 最终 Judge checkpoint、提示、温度和解析规则。
- checkpoint 选择规则。

配置：`configs/experiment3/arex_turbo.yaml`

AREX-Turbo 不训练。复用实验一命令，把划分改为 `test`：

当前 `v1.json` 的测试划分为 125 题，因此这里显式使用 `--limit 125`。如果重新生成了 split manifest，应将该值改成新 manifest 中的测试题数；`--limit 0` 会运行零道题，不能表示全量。

### 7.6 Checkpoint 选择和测试评测

所有训练方法使用 validation 划分选择 checkpoint。选择规则必须在查看 test 结果前确定，例如：

1. validation Accuracy 优先。
2. Accuracy 相同时选择 Evidence Recall 更高者。
3. 再相同时选择平均工具调用更少者。

选定 checkpoint 后，将其部署为 OpenAI 兼容策略服务，再复用实验一的 `run_benchmark.py` 和 `evaluate_runs.py` 在 test 划分运行。

正式报告至少包含：

| 指标 | 说明 |
|---|---|
| Accuracy | 最终答案正确率 |
| Evidence Recall | 最终采用证据覆盖标准证据的比例 |
| Calibration Error | 答案置信度校准误差 |
| 平均工具调用数 | 搜索成本 |
| 合法提交率 | 遵循状态协议的比例 |
| Mask density | ESR 动作信用稀疏程度 |
| 训练时间和 GPU 小时 | 训练成本 |
| 推理时间 | 每题平均耗时 |

Citation 指标可以补充，但不能代替 Evidence Recall。

## 10. 数据使用边界

BrowseComp-Plus 官方发布的 830 题原本属于同一 test 发布。本项目使用的是从该发布构造的研究切分。论文和报告中必须明确这一点。

- `train` 用于 RL rollout 和训练。
- `validation` 用于参数修改、bad case 分析和 checkpoint 选择。
- `test` 只用于方案冻结后的最终评测。

如果查看 test 轨迹、根据 test bad case 修改提示或状态规则，这些题目就不再属于未触碰测试集。此时必须重新定义测试集或明确报告数据泄漏风险。
